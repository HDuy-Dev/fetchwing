# Flows Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Flows: chain saved requests into a diagram, pass response values to later requests as variables, run it (in order and in parallel) and inspect every block.

**Architecture:** Pure logic in `src/lib/` covers the flow model, output paths, graph analysis, the run engine, run-record helpers and view math. All of it is tested with `node --test`. The panel (`src/panel/flow-*.js`) draws the canvas and the details column, and orchestrates runs in the page that pressed Run (approach B). Each non-mock block goes through the background `send` message, which gains `vars` and `key`. Run state lives in `chrome.storage.session`, so the DevTools tab and the flow window both follow a run.

**Tech Stack:** Vanilla ES modules, DOM + SVG, CSS, `node --test`. No new dependencies, no build step.

**Spec:** `docs/superpowers/specs/2026-11-26-flows-design.md` (Vietnamese). Final mockup: `mockup/flows.html`. When a visual detail isn't written here, copy it from the mockup.

## Global Constraints

- UI copy is English. Use the existing tokens in `panel.css` (dark and light). No new dependencies, no build step.
- Blocks reference requests by `requestId`. A flow never writes to a request.
- Variable precedence: flow outputs from upstream blocks, then the active environment.
- Same output name from two upstream blocks: the nearer one wins if one is upstream of the other. If they sit on parallel branches, it is a conflict and the block can't run.
- No cycles. A block runs only when all its upstream blocks are `ok`. Any upstream `failed` or `skipped` makes it `skipped`.
- Enabled mock ⇒ the block answers from the mock (status, headers, body, delay), is labelled MOCK, and calls no server. There is no per-flow or per-block mock switch.
- Run state lives in `chrome.storage.session` only. Flows (not runs) sync to Drive, last edit wins per flow.
- Zoom range 10%–400%. Below 60% blocks show only name and status icon. Snap to a 16px grid.
- Details column: default width 440px. Below 380px wide, the Inputs/Outputs rows stack.
- Heartbeat every 2 s. A run whose heartbeat is older than 6 s is abandoned.
- At most 6 blocks in flight at once.
- Sensitive values are masked by default: secret env vars; the headers `Authorization` and `Cookie`, and any header containing `api-key`; output names containing `token`, `secret`, `password` or `key`.

## Review Focus

- A workspace saved before this feature (no `flows` key), and a Drive file written by an older Fetchwing (no `flows` key): nothing is lost or reset. Covered by Task 1 and Task 2 tests.
- A response body cut at 2 MB (`bodyTruncated`) when an output points past the cut: the block is `failed` with kind `truncated`, not `missing`. Covered by a Task 5 test.
- The same request used by two blocks of one flow: each send is cancelled on its own `key`. Covered by Task 4 and Task 5 tests.
- A block whose request was deleted, or a request that uses `{{x}}` nobody provides: flagged before Run and never sent. Covered by Task 3 and Task 5 tests.
- Stop from a second window, and closing the window that runs the flow: the run stops, or ends as abandoned, and no block stays `running` forever. Covered by Task 6 tests and the Task 10 browser check.

### Task 1: Flow model and mutations

**Files:**

**Interfaces:**

### Task 3: Output paths and graph analysis

**Files:**
- Create: `src/lib/flow-path.js`, `src/lib/flow-graph.js`
- Test: `tests/flow-path.test.js`, `tests/flow-graph.test.js`

**Interfaces:**
- Produces, in `flow-path.js`:
  - `parsePath(text): { ok: true, steps } | { ok: false, error }`. The grammar is `status` | `headers.<name>` | `body` followed by steps of `.key`, `["key"]`, `[n]` or `[*]`. A step is `{ key }`, `{ index }` or `{ all: true }`.
  - `readOutput(response, path): { found: true, value } | { found: false } | { error: 'truncated' }`.
    - `response` has the shape returned by `executeSend`.
    - Header names match case-insensitively.
    - `[*]` maps over an array and drops misses.
    - A miss in a body with `bodyTruncated` returns `{ error: 'truncated' }`.
    - A body that isn't JSON returns `{ found: false }`.
  - `toText(value): string`. Strings stay as they are, numbers and booleans use `String()`, and objects, arrays and null use `JSON.stringify`.
  - `pathFor(keys: (string|number)[]): string` builds a path starting at `body`. A key containing `.`, `[`, `]` or `"` uses the bracket form, and an index becomes `[n]`.
- Produces, in `flow-graph.js`:
  - `usedVars(request): string[]`. These are the names in `{{…}}` found in the URL, enabled header keys and values, and the raw body or enabled field keys and values. Sorted and unique.
  - `upstream(flow, blockId): Set<blockId>`, all blocks upstream of the given one.
  - `topoOrder(flow): blockId[]`.
  - `analyzeFlow(ws, flow, envVars): Map<blockId, BlockInfo>`, where `BlockInfo = { request|null, uses: { name, from: blockId|'env'|null }[], missing: string[], conflicts: string[], deleted: boolean }`.
  - `edgeVars(ws, flow, edge): string[]`, the outputs of `edge.from` that the request of `edge.to` uses.
  - `blockFingerprint(request, envVars): string`, a stable JSON of `method`, `url`, `headers`, `body`, the mock (`null` unless enabled, otherwise `status`, `headers`, `body` and `delayMs`) and the env values of `usedVars`.

### Task 5: Run engine

**Files:**
- Create: `src/lib/flow-run.js`
- Test: `tests/flow-run.test.js`

**Interfaces:**
- Consumes: `analyzeFlow`, `topoOrder`, `upstream`, `blockFingerprint` (Task 3); `readOutput`, `toText` (Task 3); `withFlowVars` (Task 4); `resolveRequest` (`vars.js`).
- Produces:
  - `runFlow(opts): Promise<RunResult>`, with:
    ```
    opts = { flow, ws, envVars, send, signal, onUpdate, now, sleep,
             concurrency = 6, from = null, previous = null }
    send({ blockId, requestId, vars, key, signal }) → Promise<{ ok: true, response } | { ok: false, error, cancelled? }>
    onUpdate(blockId, BlockResult)   // called on every state change
    BlockResult = { state: 'idle'|'queued'|'running'|'ok'|'failed'|'skipped'|'missing',
                    errorKind?: 'http'|'network'|'cancelled'|'missing'|'conflict'|'deleted'|'truncated',
                    error?, response?, mock?: boolean, sent?: { method, url, headers, body },
                    outputs?: { [name]: value }, startMs?, endMs?, fingerprint? }
    RunResult = { blocks: { [blockId]: BlockResult }, totalMs, stopped: boolean }
    ```
  - `from`: a blockId for "Run from here". Blocks outside `{from} ∪ downstream(from)` are copied from `previous.blocks`, and their `outputs` feed later blocks.
  - `mockResult(mock): response`. It has the same shape as `executeSend`'s result. It adds `content-type: application/json` when the mock has no headers and the body is valid JSON, matching the page mocks.
  - Rules:
    - Before sending, `missing`, `conflict` and `deleted` blocks end as `state: 'missing'` (for missing and conflict) or `'failed'` (for deleted). They are never sent, and the blocks downstream of them are `skipped`.
    - A mock answers after `sleep(delayMs)`.
    - A status ≥ 400 is `failed` with kind `http`, and the response is kept.
    - `send` returning `!ok` is `failed` with kind `network`, or `cancelled` when it was cancelled.
    - An output that reads `truncated` is `failed` with kind `truncated`. An output that reads `{found:false}` leaves the variable unset, so the blocks downstream that use it end as `missing`.
    - `signal` aborts: running blocks become `failed`/`cancelled`, and queued blocks go back to `idle`. The result then has `stopped: true`.
    - Times are relative to the run start, using `now()`. Each send gets `key = \`${runId}:${blockId}\``.

### Task 6: Run records

**Files:**
- Create: `src/lib/flow-record.js`
- Test: `tests/flow-record.test.js`

**Interfaces:**
- Produces:
  - `RECORD_PREFIX = 'flowRun:'`, `HEARTBEAT_MS = 2000`, `STALE_MS = 6000`.
  - `newRecord({ flowId, runId, startedAt, snapshot }): Record`, where:
    ```
    Record = { flowId, runId, status: 'running'|'done'|'stopped'|'abandoned', startedAt, beatAt,
               stopRequested: false, snapshot: { flow, fingerprints: { [blockId]: string } },
               blocks: { [blockId]: BlockResult }, totalMs: null }
    ```
  - `isAbandoned(record, now): boolean`. It is true when the status is `running` and `now - beatAt > STALE_MS`.
  - `abandon(record): Record`. It sets the status to `abandoned`, and `running` and `queued` blocks go back to `idle`.
  - `blockStatus(record, blockId, currentFingerprint): { outdated: boolean }`.
  - `runFromHere(record, flow, blockId, { envChanged, outdatedIds }): { enabled: boolean, warn: string|null }`.
    - It is disabled when there is no record, when an upstream block isn't `ok` in the record, or when the upstream blocks, edges or outputs differ from `record.snapshot.flow`.
    - It warns `'Using outputs from an earlier run'` when an upstream block is outdated or the environment changed.
  - `fitRecords(records: Record[], maxBytes = 8_000_000): Record[]`. It drops the response bodies of the oldest records (by `startedAt`) until the JSON size fits. A dropped body becomes `{ dropped: true }` instead of the response text.
